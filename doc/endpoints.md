# Endpoints

This document lists the HTTP endpoints the backend serves, the
conventions they share, and how they report errors and caching.

The interactive reference at `/nightlydigest/api/docs` is generated
from the route docstrings in `main.py`, and has the full parameter and
response detail for each endpoint.

---

## 1. Base URL

Every deployment serves the API under `/nightlydigest/api`, e.g.
`https://usdf-rsp-dev.slac.stanford.edu/nightlydigest/api/exposures`.
In the local stack the same path is served through nginx at
`http://localhost/nightlydigest/api/`, and the backend can be reached
directly, without the prefix, at `http://localhost:8080/`.

The Scientific Nightly Digest does not have a backend and instead
serves static files, generated by the `scripts/generate_static_files.py`.

---

## 2. Shared parameters

**`dayObsStart`, `dayObsEnd`**: dayobs as `YYYYMMDD` integers. A
malformed dayobs, or a range whose start is after its end, is rejected
with a 422 before it reaches the endpoint.

**The end bound is not the same for every endpoint.** Most treat
`dayObsEnd` as exclusive, so `dayObsStart=20250101&dayObsEnd=20250102`
is one night. Three treat it as inclusive, so the above query is two
nights:

- `/expected-exposures`
- `/context-feed`
- `/obs-status`

**`instrument`**: `lsstcam` or `latiss`, case-insensitive. Endpoints
reject an invalid `instrument` with HTTP 422.

## 3. Endpoints

In this table, "range" means a range of dayobs specified through the
`dayObsStart` and `dayObsEnd` query parameters.

| Endpoint | Parameters | End bound | Returns |
|---|---|---|---|
| `/exposures` | range, `instrument` | exclusive | Exposure records and totals, dome-open summaries, and time-accounting metrics. |
| `/data-log` | range, `instrument` | exclusive | The full ConsDB record for each exposure. |
| `/expected-exposures` | range | inclusive | The nominal visit count from the prenight simulations, summed over the range. |
| `/almanac` | range | exclusive | One record per night: sun and moon rise and set, twilight boundaries, and twilight hours. |
| `/night-reports` | range | exclusive | Night reports, newest first. |
| `/narrative-log` | range, `instrument` | exclusive | Narrative log messages, with time lost to weather and to faults. |
| `/exposure-entries` | range, `instrument` | exclusive | Exposure log messages, in the order they were added. |
| `/exposure-flags` | range, `instrument` | exclusive | The flag on each flagged exposure. |
| `/jira-tickets` | range, `instrument` | exclusive | OBS tickets created or updated during the range. |
| `/context-feed` | range | inclusive | ScriptQueue events and related records in time order. |
| `/obs-status` | range, plus the options below | inclusive | Observatory status events, intervals and metrics. |
| `/multi-night-visit-maps` | range, `instrument`, `appletMode` | exclusive | An interactive Bokeh visit map. |
| `/static-visit-map` | range, `instrument` | exclusive | A visit map as a base64-encoded PNG. |
| `/block-details` | repeated `key` | — | Summary, URL and source for each BLOCK key. |
| `/version` | — | — | The package version. |
| `/health` | — | — | `{"status": "ok"}`, for Kubernetes probes. |

Endpoint-specific behaviour worth knowing before calling them:

- **`/almanac`** labels each night by the dayobs of its morning
  twilight, so a range returns records labelled `dayObsStart + 1`
  through `dayObsEnd`.
- **`/obs-status`** takes `includeEntries` (default true),
  `includeIntervals` (default false), `nightOnlyMetrics` (default
  true), and repeated `metric` parameters naming the metrics to
  compute; see [Observatory status metrics](#observatory-status-metrics).
- **`/expected-exposures`** counts, for each night, the visits in the
  most recent prenight simulation of that night tagged `ideal` and
  `nominal`, considering only simulations up to 60 days old, so it
  cannot return counts for nights more than 60 days ago.
- **`/jira-tickets`** matches tickets to an instrument by their
  *System* field: `LATISS` returns tickets whose system names `LATISS`
  or `AuxTel`, while `LSSTCam` returns every ticket *except* those.
  `isNew` is true for tickets created within the range, as opposed to
  older tickets updated during it. Jira's `updated` field does not
  capture every change, which has two consequences for tickets that
  are not new:
  - a ticket updated during the range drops out of it if it is updated
    again later
  - some changes, most importantly comments, do not count as updates
- **`/block-details`** takes `key=BLOCK-704&key=BLOCK-T123`, and so
  on. `BLOCK-Tnnn` keys are looked up in Zephyr Scale and `BLOCK-nnn`
  keys in Jira. If one source fails, the response is still a 200, with
  that source's message in `errors` and its keys missing from `data`,
  so check `errors` before treating a missing key as unresolved.
- **`/multi-night-visit-maps`** with `appletMode=true` returns a map
  sized for display in an applet.

Where an endpoint needs a night, it means the time between evening and
morning 12° (nautical) twilight.

### Time accounting in `/exposures`

The frontend combines these values into calculated fault time; see its
[`doc/time_accounting.rst`](https://github.com/lsst-ts/ts_logging_frontend/blob/develop/doc/time_accounting.rst).

**Dome hours**, per night, in `day_obs_open_dome_hours`:

- `night_hours`: the length of the night.
- `open_hours`: time the dome was open during the night.
- `closed_hours`: `night_hours - open_hours` for a completed night. For
  a night in progress it is the time closed *so far*: hours since
  evening twilight, less `open_hours`, and never negative.

**On-sky overhead**, in `night_on_sky_time_accounting`, covers visits
with `can_see_sky` set that start within the night:

- `visit_gap`: the time from the end of the previous visit on the same
  night to the start of this one; zero for the night's first visit.
- `overhead`: `min(modelled slew + 120 s, visit_gap)`. The slew is
  modelled between the two visits' pointings using Simonyi kinematics
  and the telescope's motion limits at the time; the 120 s allows for
  scatter the model does not capture.

Both are summed over the range in hours, and split by whether the
visit's band differs from the previous visit's, since filter changes
add their own overhead: `sum_overhead_with_filter_change`,
`sum_overhead_without_filter_change`, and the matching
`sum_visit_gap_*` pair.

### Observatory status metrics

The Scheduler publishes the observatory's state as a bitmask whenever
it changes, and a status can carry several states at once:

| State | Bit |
|---|---|
| `UNKNOWN` | none set (`0`) |
| `DAYTIME` | 1 |
| `OPERATIONAL` | 2 |
| `FAULT` | 4 |
| `WEATHER` | 8 |
| `DOWNTIME` | 16 |
| `IDLE` | 32 |

Each metric is the hours spent in a state over the range, counting only
time within the night unless `nightOnlyMetrics=false`:

- `unknown`, `daytime`, `operational`, `fault`, `weather`, `downtime`,
  `idle`: time whose status includes that state (`unknown`: no state
  set).
- `fault_loss`: time in `FAULT` but not `DOWNTIME`, so faults during
  scheduled downtime are not counted as lost observing time.

Status events exist only from dayobs 20260225. The `availability` field
reports whether the range is entirely after that (`full`), entirely
before it (`none`), or straddles it (`partial`), so that zeros before
that date are not mistaken for real data.

## 4. Errors

| Status | Meaning |
|---|---|
| 422 | A missing or malformed parameter, an inverted dayobs range, or an unknown instrument. |
| 404 | `/expected-exposures` only: no prenight simulation exists for a requested night. |
| 500 | A server fault, including missing configuration such as an unset token. |
| 502 | An upstream request failed. |
| 503 | The visit maps only: too many maps are already being built; retry later. |
| 504 | The visit maps only: the map took too long to build. |

500 and 502 errors are returned as `{"detail": "<message>"}`, with a message that
names the failing service rather than the upstream error. The upstream
exception is still logged in full.

Some endpoints degrade rather than fail when a secondary source is
unavailable: `/exposures` reports dome-open and time-accounting
failures in `open_dome_error` and `time_accounting_error` fields, and
`/block-details` reports per-source failures in `errors`.

---

## 5. Caching

Every response carries a `Cache-Control` header:

| Request | `max-age` |
|---|---|
| Range includes today's dayobs | 5 minutes |
| A mutable endpoint (`/narrative-log`, `/exposure-entries`, `/exposure-flags`, `/jira-tickets`, `/block-details`) | 5 minutes |
| Anything else | 1 day |
| Any error response | `no-store` |

The [service-adapter-infrastructure.md](service-adapter-infrastructure.md) document
covers the caching philosophy and implementation in extensive detail.
